Technical manual
320324187 - GPO06

1. Objective and scope

Develop and document an interactive 3D environment for Windows that connects planetary exploration, racing, flight and observation. The individual contribution covers the Rek’Sai avatar, its hierarchical animation, input capture and HUD, integrated with the team’s engine and world.

The implemented scope includes a space base and three surfaces: rock, forest and ocean. Zone transitions change state and scene; they are not continuous landings on a sphere. F1-F4 select experiences. Follow, chase, flight and orbit camera rigs determine how each experience is viewed.

Limitations

Window::Initialise requests an OpenGL 4.3 Core context, although earlier documentation referred to 3.3. The target is Windows x64 with C++17 and toolset v143. There is no biological simulation or general physics engine. Delivery textures were reduced to at most 512 × 512, which reduces visual detail. No performance benchmark or independent second-computer test is available.

Technical background

Programmable rasterization separates vertex attributes, transformations, texture sampling and per-fragment lighting [1]. The project uses this pipeline for imported models and procedural geometry. GLFW manages the window, context and events [2]; GLM supplies vector and matrix types [3]; Assimp reads model files into an imported scene [4]. Animation uses hierarchical transforms, parametric paths and keyframes, making the mathematics of each frame explicit.

Actual code structure

Main.cpp coordinates the loop, zones, lights and infrastructure actions. SceneVerification.cpp contains integrated checks, not a second main. src/engine contains Window, Model, Texture, Shader_light and light classes. src/scene contains SceneNode, Scene and CameraDirector with FollowXZ, Chase, Flight and Orbit. src/game/world contains Superficie, Espacio, Oceano, Jugador and Reloj. Avatar.cpp and Tars.cpp manage articulated models. Input.cpp separates capture from mapping; src/ui/Hud.cpp draws state. CoheteKeyframes.h loads and plays twenty channels for the multipart rocket.

3. System flow and contracts

Data, ownership and ordering

InputCapture updates held keys, press edges, mouse motion and wheel input. The delivery fix preserves presses released within one glfwPollEvents call and consumes each event once. CameraDirector mode and active zone are independent states. Normal frame time is capped at 0.05 s; animation tests use a fixed 1/60 s step.

SceneNode owns children through unique_ptr and holds borrowed graphics-resource references. updateWorld propagates matrices before cameras and rendering consume them. Avatar::attach classifies OBJ groups and builds nine parts with local pivots. Model::LoadModel imports meshes and materials; resolverRutaTextura resolves relative resources. PrepararRecursosSuperficie prepares planets on demand.

Startup locates Models and Textures relative to the executable and its parent directories. Window::Initialise centers the window in the primary monitor’s work area. The context is created before GPU resources are loaded. Readable sources, the solution and local dependencies are included.

4. Transforms and lighting

SceneNode::local builds Mlocal = T · Ry · Rx · Rz · S. updateWorld computes Mworld = Mparent · Mlocal. A part’s point is transformed locally and then inherits its parent’s transform. Rotation about a hinge p uses T(p) · R(θ) · T(-p); Main.cpp applies this to the capsule and CoheteKeyframes::Dibujar to rocket parts.

shaders/shader_light.frag computes ambient, diffuse and Phong-style specular reflection: Id = kd · max(N·L,0) and Is = ks · max(V·R,0)^s. Point lights are attenuated with distance; spotlights add a cutoff cone. Materials control shininess and specular intensity. Emission supplies self-brightness, rather than illumination received by geometry.

The lighting cycle uses θ = 2πt/120 and sunHeight = sin(θ). A clamped day factor preserves ambient light and controls lamps. F, L and K toggle three spotlights. Captures show deliberately dark areas; the presence of a shader alone does not establish that lighting is free from defects.

Figure 1. Rock zone: avatar, capsule, crystals and lamps in the Release render.

5. Seven animation systems

The count groups repetitions and all parts of a gait. The keyframed rocket is distinguished from procedural launch because it combines multipart staging and orbit across twenty channels, whereas the latter uses a state machine and accelerated ascent. Acceptance of this distinction belongs to the evaluator; parametric NPCs in Superficie::MatrizNPC and the Fighter departure/return provide additional implemented candidates.

Animation mathematics and testing

1. Rek’Sai

Opposing legs: 0.78 sin(φ) and 0.78 sin(φ+π). Arms, head and tail share that phase; φ advances with dt and speed.

2. Keyframed rocket

20 channels; α=(t-ti)/(ti+1-ti); v=(1-α)vi+αvi+1. Includes translation, pivot rotation, staging and orbit.

3. Procedural rocket

Ascent h=Hτ², with τ clamped to [0,1]; ignition vibration and orbital oscillation.

4. Doors

Capsule: θ←θ+(θtarget-θ)min(1,6dt), around a local hinge. Hangar: clamped two-second opening.

5. Satellite panels

Factor interpolated toward 0/1, rotation toward ±85° and opposing oscillations when deployed.

6. Satellite trajectory

Two parametric lobes; a normalized tangent orients the object. θ←θ+ωdt; the guide adjusts parameter steps using derivative magnitude.

7. Rival ships

d=(offset+18t) mod L. Accumulated distance selects a segment; position and tangent frame come from track, surface or ocean.

Run LabCGeIHC.exe --probar-animaciones. The sequence injects events through the same GLFW callback used by the keyboard, advances 3360 frames at dt=1/60 and captures every 120 frames. It activates 6 in rock, F4/1 for D1, Tab/4 for the hangar, Tab/3 for the satellite, F2 for rivals and F1/W for gait. It does not replace manual review of framing, intersections or artistic quality.

Individual conclusion

Working on Rek’Sai connected geometry groups, pivots and matrices with visible motion. A gait requires coordinated parts rather than unrelated leg rotations. Integration with input, cameras and HUD required a clear separation between user intent, world state and presentation. I also learned that compilation alone does not ensure that another person sees a window or finds the assets. Documenting the code and repeating complete executable tests helps distinguish an implemented function from a verified experience.

System conclusion and delivery limits

The scene combines transforms, synthetic cameras, lighting and procedural animation in a shared application. Functional roles helped integrate models and experiences, but external resources and outdated documentation caused discrepancies. The current preparation improves portability, size and traceability without replacing outstanding tests. The evaluated version must be identified by the entrega/320324187-teoria branch and its commit, rather than main alone. Publication is recorded in the verification report.
